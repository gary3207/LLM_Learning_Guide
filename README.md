# 📘 작은 모델부터 배우는 LLM · MLOps

**Linux 환경 준비부터 텍스트 분류·평가·토큰 생성까지, 코드를 실행하며 원리를 익히는 한국어 학습 가이드입니다.**

작은 예제로 **데이터 → 학습 → 저장 → 추론 → 평가**의 흐름을 이해한 뒤, 문장을 한 토큰씩 생성하는 과정과 문맥의 역할을 살펴봅니다. 완성된 챗봇을 바로 만드는 대신, 각 계산과 출력의 의미를 설명할 수 있는 것을 목표로 합니다.

## 🛠️ 실습 환경과 실행 위치

- 환경 예시: **Ubuntu + Python 가상환경 + PyTorch**.
- GPU 계산과 분류기 학습 예제는 NVIDIA CUDA 환경을 사용합니다. 다음 토큰 예측과 두 토큰·세 토큰 문맥 모델은 CPU에서 실행하는 코드입니다.
- 기본 실습 폴더는 `~/llm-lab/source`입니다. 이 저장소의 장별 `source/` 경로와 구분합니다.
- 체크포인트를 저장하는 코드는 파일 위치에 의존할 수 있습니다. **각 장에서 지정한 VM 경로·파일명으로 배치한 뒤 실행합니다.**
- 드라이버·CUDA·패키지 버전은 설치 환경과 지원 조합을 확인합니다. 특정 버전을 모든 환경에 그대로 적용하지 않습니다.

> [!WARNING]
> 코드를 한꺼번에 실행하지 마세요. 각 장의 선행 파일과 저장 경로를 확인하고 순서대로 진행합니다. 기존 체크포인트 보호 검사를 제거하거나, 재실행을 위해 원본 모델을 임의로 삭제하지 않습니다.

## 🔬 실행 예시와 해석

아래는 예제 데이터와 설정의 **참고 출력**입니다. 패키지·장치·난수 처리에 따라 loss와 예측이 달라질 수 있으므로, 동일한 숫자보다 계산 흐름과 검사 조건을 이해하는 것이 중요합니다.

| 실습 | 실행 예시 | 해석의 범위 |
|---|---|---|
| 데이터 분리 | train 10 / validation 4 / test 3 | 교육용 소규모 데이터; 운영 평가를 대표하지 않음 |
| 두 분류 모델 검증 | 정확도 모두 3/4, 75.0% | 동률일 때 미리 정한 보조 기준 적용 |
| 검증 loss 비교 | 원본 0.8041 / 보완 0.7280 | 이 예시에서는 보완 모델 선택 |
| 선택 모델 테스트 | 3/3, 100.0% / loss 0.2959 | 세 문장 결과만으로 다른 오분류 해결을 단정할 수 없음 |
| 한 토큰 모델 | 학습 쌍 9/9 / 최종 loss 0.0055 | 학습 문장 재현이지 일반화 성능은 아님 |
| 두 토큰 모델 | 학습 쌍 6/6 / loss 1.6644 → 표시값 0.0000 | 반올림된 표시값이며 정확한 0을 뜻하지 않음 |
| 세 토큰 모델 | 학습 쌍 8/8 / loss 2.3490 → 표시값 0.0000 | 학습 쌍 적합 결과; 복원·생성은 별도 검사 |
| 문맥별 생성 | `gpu status failed`, `network status healthy` / `<eos>` 종료 | 복원·문맥 이동·종료·길이 제한 확인 |
| 세 토큰 문맥별 생성 | `gpu current status failed`, `network current status healthy` / `<eos>` 종료 | 저장 모델 복원·마지막 세 토큰 입력·양쪽 길이 제한 검사 통과 |

> [!IMPORTANT]
> 검증 문장 중 일부는 앞선 오류 분석에서도 사용합니다. 이 구성은 **평가 절차를 배우는 예제**이지, 완전히 새로운 문장에 대한 엄격한 블라인드 평가가 아닙니다. [평가 설계의 한계](04-evaluation.md)를 함께 읽으세요.

## 🌱 다루는 범위

선형 분류기와 고정 길이 문맥 모델로 학습·저장·복원·평가·생성을 익힙니다. 이 모델들은 Transformer나 대화형 LLM이 아닙니다. Attention 입문은 QKV 선형 변환·비중 계산·Value 가중합·causal mask·위치 표현에서 시작해 어휘 출력·loss·기울기·출력층 학습 루프와 자동 미분 비교를 다룹니다. 마지막 연결 실습은 고정 입력에서 QKV와 어휘 출력 행렬을 함께 한 번 갱신합니다. 09장은 고정 입력의 단일-head Attention에 잔차·LayerNorm·FFN을 붙인 작은 블록을 한 번 갱신합니다. 10장은 학습되는 토큰·위치 임베딩을 연결해 두 예문 모든 입력 위치의 다음 토큰 정답을 학습합니다. 11장은 같은 작은 블록 기반 모델을 별도 저장하고 새 프로세스에서 복원해 학습 예문을 반복 생성합니다. 엄격한 독립 최종 평가는 별도 과제이며 이후 장에서 사전학습 모델·LoRA·QLoRA·서빙으로 확장합니다. RAG는 이 가이드의 후속 학습 범위에 포함하지 않습니다.

12장은 모델을 바꾸지 않고 새 입력의 반응을 정성적으로 관찰합니다. 13장은 합성 정답과 형식별 분리로 마지막 상태 위치를 평가합니다. 소수 예제의 진단 평가이며 넓은 일반화나 모델 선택의 완료를 뜻하지 않습니다.

14장은 원본을 보존하고 복사본 둘을 같은 조건으로 추가 학습해 데이터 표현 보완을 비교합니다. 이전 test는 개발용으로 구분하며 독립 최종 평가·문장 생성 유지 검증은 포함하지 않습니다.

15장은 보완 후보 재현·생성 회귀 확인·별도 저장·새 프로세스 복원을 한 흐름으로 묶어 작은 모델 실습을 마무리합니다. 상태 정답 개선과 생성 유지 실패, 재현 성공과 품질 개선을 구분합니다.

16장은 사전학습된 SmolLM2-135M-Instruct와 토크나이저를 불러와 CPU에서 질문 토큰화·대화 템플릿·마지막 위치 점수·greedy 응답 생성을 관찰합니다. 로컬 다운로드·추론·캐시 오프라인 재실행을 검증한 예제이며 새 학습이나 사실성 평가가 아닙니다.

17장은 같은 모델을 두 합성 질문·응답으로 SFT하고, 학습 질문과 표현 변경 probe에서 기본 모델 대비 loss·생성을 비교합니다. 원본을 보존하며 별도 저장·새 프로세스 복원까지 실행합니다. 전체 파라미터 CPU 학습의 작은 예제이며 독립 최종 평가·넓은 생성 회귀는 포함하지 않습니다.

18장은 같은 원본·데이터·SGD 설정에서 q/v rank4 LoRA만 학습하고 작은 어댑터를 저장·복원합니다. CPU 검증과 별도 A10 CUDA 실행 로그에서 loss는 낮아져도 정답을 생성하지 못한 결과와 복원 성공을 함께 확인합니다. 학습 대상 수 감소와 품질·GPU 메모리·속도를 구분합니다. QLoRA는20장, 서빙은21장 이후로 연결합니다. RAG는 후속 학습 범위에서 제외합니다.

19장은 기존 원본·SFT·LoRA를 재학습 없이 같은 평가 장치·생성 조건으로 실행하고, 학습 질문·기존 probe·추가 진단의 정답률과 응답/eos loss를 따로 집계합니다. 문항별 생성·오류 분류와 설정을 JSON으로 저장합니다. 미학습 fixture의 CPU 코드 검증과 별도 CUDA 학습 후보 평가를 구분합니다. CUDA 추가 진단은 원본0/4·SFT3/4·LoRA0/4이며, SFT의 잘못된 상태 라벨과 LoRA의 loss 감소/정답 수 유지도 수록합니다. 독립 최종 평가·자동 모델 선택은 포함하지 않습니다.

20장은 같은 원본을 NF4·이중 양자화로 로딩하고 q/v rank4 어댑터만 새로 학습·저장·복원합니다. 실제 CPU 검사와 별도 A10 CUDA 로그 모두 원본/양자화 상태 유지·어댑터 저장·복원 통과를 확인했지만 loss 감소가 한 단어 정답 생성으로 이어지지는 않았습니다. 연산은 float32인 교육용 구성으로 논문 전체 재현·성능 벤치마크와 구분합니다. 기존 후보는 유지하고 서빙은 다음 묶음으로 남깁니다.

21장은 저장한 QLoRA를 읽기만 하고 Python 표준 HTTP 서버로 요청·응답을 연결합니다. 같은 VM의 두 터미널에서 health와 두 생성 요청을 보내고 Ctrl+C로 종료합니다. CPU 미학습 fixture의 코드 검사와 별도 CUDA HTTP200 실행 예시를 구분합니다. CUDA 응답은 입력41·40토큰/새8토큰씩이지만 한 단어 정답 생성은 실패했으며, API 성공과 품질을 구분합니다. 외부 공개·운영 배포·동시 처리·품질 개선은 포함하지 않습니다.

22장은 같은 저장 QLoRA를 측정 옵션으로 호출해 워밍업과 반복 측정을 구분하고, HTTP 지연·동기화한 생성 시간·실제 토큰/초·CUDA allocator 메모리를 기록합니다. CPU 코드 검사와 별도 CUDA 실행 예시를 구분합니다. CUDA 측정10건은 HTTP 중앙값447.73ms·생성17.93토큰/초·최대peak allocated176.04MiB/peak reserved316.00MiB였고 한 단어 정답 생성은 실패했습니다. TTFT·동시 부하·장시간 안정성·재학습·외부 공개는 포함하지 않습니다.

23장은 기존 QLoRA 폴더·설정·성능 보고서를 경로/해시로 등록하고 무결성 확인 후 선택 정보를 기록합니다. 로컬 합성 파일 검사와 별도 VM 실행 예시를 구분합니다. VM에서는 `qlora-v1`·모델 파일11개·성능 보고서7,260bytes 등록과 선택·show 재검사를 확인했습니다. 원본 복사·학습·품질 합격·과거 실행 lineage 증명·배포는 포함하지 않습니다.

24장은 선택한 등록 버전을 검증하고 기존 API 로더로 복원한 뒤 health·생성 응답에서 같은 `model_version`을 확인하는 실습입니다. 시작 시점의 버전·manifest 지문·원본 ID/revision을 고정하며, 이후 선택 변경은 종료·재시작해야 반영됩니다. 로컬 CPU 미학습 fixture 검사와 별도 CUDA VM의 `qlora-v1`·health/생성 동일 식별 정보·입력41/새8토큰 응답을 구분합니다. VM 정상 종료는 아직 미확인이며, 재학습·레지스트리/모델/보고서 수정·실시간 파일 감시·동시 변경 보호·외부 공개·품질 보증은 포함하지 않습니다.

## LLMOps 후속 실습

25장은 기존 선택 QLoRA를 생성 평가하고 미달이면 보고서를 남겨 해당 실행 경로의 서버 시작을 차단합니다. 로컬 CPU 미학습 fixture 검사와 별도 CUDA VM의 `qlora-v1`·8문항0정답·종료2·`approved: false` 보고서 조회를 구분합니다. 모델 품질 미달과 게이트 동작 성공은 별개이며, 합격 후 서버 시작은 이번 CUDA 실행에서 수행하지 않았습니다.

26장은 새 평가 실행 시점의 코드·데이터·설정·모델·보고서를 실행 ID로 연결하고 조회합니다. 별도 CUDA VM에서는 기존 `qlora-v1`의 새 평가0/8·blocked·실행 종료2와 기록 조회 종료0을 확인했습니다. 품질 미달 결과도 정상적으로 추적된 예시입니다. 기존25장 보고서를 사후에 완전한 실행 이력으로 바꾸는 것이 아니며 모델·코드 자동 백업이나 동일 출력 보장은 아닙니다.

27장은26장 추적기를 재사용해 새 평가→결과 검증→다음 단계 허용/중단을 한 명령으로 연결합니다. 별도 CUDA VM에서는 `qlora-v1`의0/8·Evaluate=blocked·Verify=passed·Decision=halted_quality·종료2·followup=skipped/deployed=false를 확인했습니다. 승인0·품질 미달2·실행 오류1을 구분하고 같은 실행 폴더에pipeline.json을 남깁니다. 실제 서버 시작·배포·등록/선택 변경은 하지 않습니다.

28장은 명시한27장 실행의 근거를 읽고 승인된 버전만 전용systemd 사용자 서비스로 전환합니다. HTTP 식별 정보 확인 뒤 확정하고 실패하면 이전 검증 배포로 복구합니다. 품질 미달은 서비스/상태 변경 전 종료2이며,selected 포인터는 변경하지 않습니다. 별도 CUDA VM에서는 기존 품질 미달 실행의 배포 종료2·DEPLOY_STATE_EXISTS=False를 확인했습니다. 로컬 네이티브 unit/합성transport 검사와 실제NF4/테스트 수명관리 검사를 구분하며 학습 모델의 실제 승인 배포·롤백은 아직 미실행입니다. 다음 묶음은 운영 관찰·부하 검사입니다.

품질 검증·승인 → 실험 추적·재현성 → 파이프라인 → 배포·롤백 → 운영 관찰·부하 검사 → Docker 실행환경 패키징 순서로 연결합니다. 현재 구현 범위와 이후 계획은 [로드맵](00-roadmap.md)의 LLMOps 묶음 표에서 구분합니다. RAG는 포함하지 않습니다.

29장은 기존24장 서버를 별도 loopback 진단 포트에서 `--metrics`로 실행하고 작은 순차/동시 요청 묶음을 비교합니다.22장의 집계를 재사용하며 오류·성공 지연·단계 wall time 처리량·CUDA allocator 메모리를 새 보고서에 기록합니다. 별도 CUDA VM에서는 각6건 성공/0실패·보고서 저장·종료0, 순차/동시 지연 중앙값453.99/1359.58ms·단계 처리량17.63/17.64토큰/초를 확인했습니다. 요청이 겹치면서 지연이 늘었지만 처리량은 거의 같았습니다. 단일 요청 서버를 GPU 병렬 실행으로 해석하지 않으며 품질 미달 판정·배포 거부는 유지합니다. 서버 정상 종료는 별도 미확인이고 다음 묶음은 Docker 패키징입니다.

30장은 기존21·23·24장 코드를 Docker 이미지로 패키징하고 실제 CUDA VM에서 기존 모델·레지스트리·캐시를 읽기 전용으로 연결했습니다. 이미지 빌드/검사0, Python3.12.15·주요 여섯 패키지·CUDA12.8, 모델cuda:0·NF4 210·전체 health identity 일치·순차/동시 각2성공0실패·새 보고서/검사0과 대상 컨테이너 제거를 확인했습니다. A의 정상 종료 문구 자체는 미제공입니다. 이로써 LLMOps 입문 여섯 묶음의 학습 범위를 정리했지만 품질0/8·실제 승인 배포/롤백 미실행은 유지합니다. 다음 학습은 독립 평가 데이터·모델 품질 개선·학습 재현/재개·작은 모델 구조 확장입니다. RAG는 제외합니다.

31장은 합성 규칙을 유지하며 문장 틀 단위로 train8/dev4/test4와 기존 진단6개를 분리합니다. 표준 라이브러리로 데이터 생성·중복/정답/그룹 검사·JSON 읽기 일치·덮어쓰기 거부를 로컬 검증했습니다. 별도 Ubuntu VM에서도 코드 생성·같은 문항 수·CHECK=PASS·JSON 저장·모델 실행/학습 없음과 셸 복귀를 확인했습니다. 기존 품질 판정은 변경하지 않습니다. 두 장치의 작은 표현 보류 평가 준비이지 블라인드 시험이나 실제 장애 진단 검증이 아닙니다. 다음 묶음은 모델 품질 개선입니다.

32장은 기존 어댑터에서 출발해31장 train8개로 추가0/20/60회 시점을 비교합니다. 별도 CUDA VM에서 cuda:0·NF4210·학습대상230400, 세 시점 train0/8·dev0/4와 dev loss9.391413→7.103381→3.677019를 확인했습니다. dev 동률에서 loss로60회를 선택했고 새 프로세스 dev 생성/logits 복원 통과·최종 test 기준/선택 모두0/4·보고서 저장과 셸 복귀를 확인했습니다. 학습량 비교 실습은 완료됐지만 정답률 개선은 없었습니다. 로컬 미학습 fixture와 시작 조건을 구분하고 기존 입력 모델·레지스트리·게이트는 유지합니다. 다음 묶음은 optimizer·scheduler·난수 상태를 포함한 학습 재개입니다.

33장은 기존 어댑터에서 새 AdamW/StepLR 실험을 시작해 연속6회와 중간3회 저장·별도 프로세스3회 재개를 비교합니다. 로컬 CPU fixture 검증과 별도로 CUDA VM에서도 cuda:0·NF4210·학습대상230400, 기준/분할 경로 문항·학습률·표시 loss 일치, VERIFY=PASS·최종 어댑터 최대 차이0·보고서 저장·셸 복귀를 확인했습니다. 재개한4~6회 loss는6.891398/5.935735/5.478755로 연속 경로와 같았습니다. optimizer/scheduler/Torch RNG를 포함한 재개 실습 완료이며 모든 환경 비트 동일성이나 정답률 개선을 뜻하지 않습니다. 기존 모델/32장결과/레지스트리/게이트는 유지하고 다음 묶음은 작은 모델 구조 확장입니다.
